## 0. 점검 방법과 표기

커리큘럼 요구: "보안 체크리스트로 자기 코드 전체 점검·수정, 권한 축소 사용자로 재현 → 결과표(수정 전/후)".

| 표기      | 뜻                                                                                                           |
| --------- | ------------------------------------------------------------------------------------------------------------ |
| **[AI]**  | Claude가 1차 점검한 것 — 클래스 원문 판독, 레포 전체 grep, 테스트 작성, 디버그 로그 판독, RunLocalTests 실행 |
| **[Kai]** | 본인이 재현 · 검증한 것 — 김 길동(SV) Login As 화면 확인 · 캡처, Setup의 FLS 확인, 판단 결정                 |
| ○ △ ×     | ○ 의도한 설계 · △ 검토 필요 · × 이번에 수정함                                                                |

- 권한 축소 사용자: **김 길동**(가맹점점검 SV, 담당 매장만). 새 사용자는 만들지 않았다 — Platform 라이선스 잔여 0, 사용자는 삭제 불가.
- Apex 테스트의 runAs 사용자는 `TestDataFactory.createSvUser`가 테스트 안에서만 만든다(라이선스 미사용).

**2-b에서 확인한 예외** [AI — 디버그 로그 판독]

```
System.DmlException
getDmlType(0)       = CANNOT_INSERT_UPDATE_ACTIVATE_ENTITY
getDmlFieldNames(0) = (Judgement__c)
message             = Operation failed due to fields being inaccessible on Sobject Inspection__c, ...
```

예외 타입을 추측하지 않고 `Exception`으로 먼저 받아 로그로 확인한 뒤 `DmlException`으로 좁혔다. 테스트는 메시지와 **막힌 필드가 `Judgement__c`인지**까지 Assert한다.

테스트 설계에서 지킨 것:

- 트리거가 판정을 덮어쓰는 조건(상태가 점검완료로 바뀔 때 · 점검완료에서 Roll-Up 점수가 바뀔 때)을 피하려고 대상 점검은 **점검예정**으로 만든다.
- `Assert.fail`을 try 안에 두지 않는다 — `catch`가 그 실패까지 삼켜 거짓 통과한다.
- 레코드 층 테스트는 `@TestSetup`을 쓰지 않는다 — 같은 클래스의 기존 테스트가 전체 건수를 Assert한다.
