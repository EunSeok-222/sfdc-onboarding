## D6 · 2026.10.12 — 테스트 · 비동기 · 설정 데이터

출처: daily-log D6 「결정과 이유」 1 ~ 5

- **판정 테스트는 DB를 타지 않고 `JSON.deserialize`로 Roll-Up 값 주입** — 판정은 Roll-Up 세 값만 보는 순수 계산이다. 경계값마다 insert하면 SOQL · DML이 배로 늘어난다.
- **실패 테스트는 "막혔다"가 아니라 "이 이유로 막혔다"까지 검증** — 저장 실패만 보면 다른 이유로 막혀도 통과한다. `Database.update(ins, false)`로 오류 메시지와 필드까지 Assert한다.
- **BR-05 지연 처리는 Batch + Schedulable** — "한 트랜잭션 한도를 넘는가"로 골랐다. 가맹점이 늘면 쿼리 행 50,000을 넘으므로 청크마다 한도가 리셋되는 Batch여야 한다.
- **Batch는 호출만, 로직은 Service** — D5의 "트리거는 호출만" 원칙을 실행 방식만 바꿔 적용. 같은 로직을 배치 · 화면 · 테스트에서 같은 입구로 부른다.
- **기준값은 Custom Setting이 아니라 Custom Metadata** — 합격선 · 시정선은 값까지 운영 org로 따라가야 하는 업무 정책이다. Custom Setting은 데이터를 org마다 다시 넣어야 한다.

## D7 · 2026.10.13 — LWC 기초 · 데이터 연동

1. **상세(SC-02)는 `lightning-record-form`(LDS)로, Apex 없이** — 레코드 1건 CRUD는 캐시 · 동기화 · FLS를 플랫폼이 준다. 판정 패널만 `@wire(getRecord)`: `recordId` 하나로 조회가 정해지기 때문.
2. **목록(SC-04)은 칩 · 검색 · 정렬 · 페이징 전부 imperative 한 경로로** — 처음엔 칩만 `@wire`로 생각했으나, 같은 Apex를 두 방식으로 부르면 늦게 온 응답이 화면을 덮어쓰고 조건 객체도 둘로 갈라져 통일했다. 정렬 · 페이징은 서버(`ORDER BY` · `LIMIT/OFFSET`), OFFSET 최대 2,000은 알고 선택.
3. **칩은 LWC가 "칩 → 상태 목록"을 갖고, Apex는 `Status__c IN :statuses`만** — 업무 묶음이 바뀌어도 Apex는 그대로. 칩은 해야 할 점검(점검예정) · 시정 대기(시정중 + 지연) · 전체 3개. 「점검중」은 요건서 §3과 D5 전이표 어디에도 없는 값이라 제외(설계 초안 오류).
4. **판정(`Judgement__c`)은 레이아웃 Read-Only + FLS 읽기 전용, 두 겹을 유지** — 관리자 화면에서 판정에 연필이 보여 org를 확인했더니, 권한 매트릭스 V1.2대로 레이아웃 `Readonly` · SV · 권역팀장 · 조회전용 FLS 편집 불가가 **이미 걸려 있었다**. 연필은 System Administrator의 "Edit Read Only Fields" 권한 때문이라 org 설정은 바꾸지 않았다. 둘 다 필요한 이유: D5에서 판정을 점검완료 · 점수 변경 때만 계산하게 했으므로 손으로 고친 값을 아무도 되돌리지 않고, 레이아웃 Read-Only는 관리자 권한으로 넘을 수 있어 FLS가 진짜 잠금이다. 트리거는 시스템 모드라 계속 쓴다. 확인은 관리자가 아닌 김 길동 계정으로.
5. **에러는 `reduceErrors({ body: event.detail })` + `ShowToastEvent`(sticky)** — record-form 에러에는 `body`가 없어 그대로 넘기면 D5 메시지 대신 일반 문구가 나온다.

### 구현하면서 추가로 정한 것

- **목록 조회는 `Database.queryWithBinds(..., AccessLevel.USER_MODE)`** — 바인드 값을 맵으로 넘겨 사용자 입력이 SOQL 문자열에 섞이지 않게 하고, sharing에 더해 FLS까지 현재 사용자 기준으로 강제한다. 정렬 컬럼 · 방향은 바인드할 수 없어 화이트리스트로 검증한다.
- **정렬 끝에 `NULLS LAST, Name ASC`를 붙여 순서를 고정** — 점검일이 같은 행이 여럿이면 DB가 순서를 보장하지 않아 OFFSET 페이징에서 중복 · 누락이 생긴다.
- **목록은 한 컴포넌트로 먼저, 칩 · 검색창 · 페이저 분리는 D8** — 나누는 건 코드를 옮기는 일이라 언제든 할 수 있지만, 처음부터 나누면 깨졌을 때 어느 경계의 문제인지 가리기 어렵다.
- **시연 데이터는 되돌리지 않고 매번 새로 만든다(`scripts/apex/`)** — 점검완료 → 점검예정은 D5 트리거가 막는다. 시연용 레코드에는 `DEMO-` 표시를 달아 리허설로 생긴 시정조치까지 찾을 수 있게 한다.

## D8 · 2026.10.14 — 보안 증명 · AI 제안 중 채택하지 않은 것

출처: `docs/d8-security-review.md` 7장. 세 건 모두 AI가 제안했고 Kai가 채택하지 않았다.

1. **시연용 「내부 메모」 필드를 만들지 않고, 기존 `Judgement__c` 편집 FLS로 필드 층을 증명** — 요건서 V1.0 · ERD V1.0 · 권한 매트릭스 V1.2 어디에도 없는 시연 전용 필드라, 만들면 발표를 위해 요건을 만드는 셈이 된다. 읽기 FLS는 "요건상 숨길 필드 없음"으로 결과표에 적었다. 제안은 계획 수립 중 2회(Claude Code 수정본, 브라우저 Claude). 그대로 갔다면 요건에 없는 필드가 산출물 3종에 거꾸로 추가됐을 것이다.
2. **`with sharing`을 뺀 코드를 org에 임시 배포하지 않고, `System.runAs` 테스트 4건으로 보호가 작동함을 증명** — 보호를 벗긴 코드를 org(kai-dev)에 올리면 복구 누락이나 배포 실패로 중간 상태가 남을 위험이 이득보다 크다. 대가로 "보호가 없던 화면" 캡처는 없다.
3. **외부 위생등급 조회(HACCP) 연동을 하지 않고, 연동 후보는 BR-08 후단(공급 제한 승인 즉시 물류팀 통보)으로** — HACCP 연동은 요건서에 근거가 없다. BR-08 통보 연동은 요건서 As-Is 「승인·통보 지연」(공급 제한 통보 지연으로 제한 기간에 출고 발생)을 직접 푼다.

### 하루 요약 — 결정한 것과 이유

1. **보안 필드 층은 기존 판정(`Judgement__c`) 편집 FLS + runAs 테스트 4건으로 증명** — 시연용 「내부 메모」 필드는 요건서 · ERD · 권한 매트릭스 어디에도 없어 발표를 위해 요건을 만드는 셈이고, `with sharing`을 뺀 임시 배포는 org에 위험을 남긴다. (상세: 위 1 · 2번)
2. **최근 정기점검일 갱신 한 줄만 `update as system`으로 수정** — SV로 재현하니 FLS 때문에 점검완료 저장이 실패했다(관리자 테스트로는 못 잡음). 권한을 넘는 범위를 그 한 줄로 좁혔다.
3. **심화 요건은 BR-08 「공급 제한 승인 즉시 물류팀 통보」 콜아웃 스텁(Named Credential + Mock)** — 요건서 As-Is의 통보 지연을 직접 푸는 연동이다(HACCP를 하지 않은 이유: 위 3번). 승인 저장 중에는 동기 콜아웃이 불가해 호출부는 Queueable로 분리한다.
4. **프록시 503(ERR_DNS_FAIL)은 코드를 바꾸지 않고 문서로 남김** — 주소 오류도 예외가 아니라 503으로 와서 상태코드만으로는 상대 장애와 우리 설정 오류를 구분할 수 없다. 503은 재시도로 두고, X-Squid-Error 판별 기준은 인터페이스 정의서에 적는다.
5. **10/19 발표는 현장 흐름(점검 → 판정 → 시정조치 → 매장 이력)을 중심으로** — 구현과 테스트가 가장 많이 쌓인 경로이고, 아직 못 푼 두 가지(SV 페널티 공유 경로, Queueable 연결)가 시연 한가운데 오지 않는다.
