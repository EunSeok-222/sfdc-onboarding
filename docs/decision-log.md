## D2 · 2026.10.02 ~ 10.05 — 권한 · 데이터 모델

출처: daily-log D2 「결정 사항」, ERD V1.0 §3

- **데이터 모델은 Account + 커스텀 오브젝트만** — 테스트 사용자 3명이 Platform 라이선스라 Opportunity · Case · Campaign을 쓸 수 없다.
- **최 대표(경영진)는 Role 계층 밖에 두고 Public Group `ExecutiveViewers` + 공유 규칙으로 읽기 전용 열람** — 계층에 넣으면 읽기뿐 아니라 쓰기까지 상속된다.
- **점검 → 가맹점은 Lookup** — 점검마다 담당 SV가 소유자여야 하고(비공개 설계), 가맹점을 해지해도 점검 이력은 남아야 한다(ERD §3).
- **결과 항목 → 점검, 시정조치 → 결과 항목은 Master-Detail** — Roll-Up Summary와 권한 상속이 필요하다.
- **결과 항목은 템플릿 값을 스냅샷 복사, 템플릿 Lookup은 추적용** — 점검표 양식이 바뀌어도 과거 점검은 당시 항목 · 배점을 유지해야 한다(요건서 BR-11 · ERD §3).

## D3 · 2026.10.06 ~ 10.07 — 선언형 자동화 · 이관 · 리포트

출처: daily-log D3 「결정 사항」 #1 ~ #5

- **시정조치 기한 · 재방문 여부는 Before-Save Flow** — 자기 필드만 채우므로 DML 없는 Before가 가장 빠르다. 판정처럼 예외 · 테스트가 필요한 계산은 Apex로 넘긴다.
- **페널티는 Approval Process, 승인자 = 소유자의 Manager 필드** — 결재와 잠금이 필요한 규칙이고, Manager 지정이라 SV 재배치에도 프로세스를 고칠 필요가 없다.
- **배정은 Assignment Rule 대신 미배정 점검 Queue** — Assignment Rule은 Lead · Case 전용이고 Platform 라이선스는 Case 불가. 대가로 Queue 소유 레코드는 계층 · 소유자 기반 공유에서 빠진다.
- **대시보드는 동적(대시보드 뷰어)** — 지정 사용자로 두면 SV가 다른 SV의 점검 건수까지 보게 된다.
- **이관은 External ID upsert, 부모 → 자식 순서** — 재실행해도 중복이 생기지 않는다.

## D4 · 2026.10.08 — Apex 서비스 · 벌크 안전

출처: daily-log D4 「결정 사항」 #1 ~ #5

- **`InspectionService`는 `with sharing`, 공유를 넘는 작업은 별도 클래스** — 화면 · 트리거 · Batch 어디서 불려도 호출자의 공유 범위를 지킨다. 선언을 생략하면 호출 맥락에 따라 동작이 달라진다.

- **판정은 결과 항목을 조회하지 않고 Roll-Up 필드만 읽는다** — 결과 항목을 M-D로 묶은 ERD 결정 덕분에 SOQL 1회로 끝난다.
- **가맹점별 점검 건수는 Apex 집계(GROUP BY)** — 가맹점–점검이 Lookup이라 Roll-Up Summary를 쓸 수 없다(ERD의 대가).
- **판정 기준 0.8 / 0.6은 일단 코드 상수, D6에 Custom Metadata로 이관** — D4 목표는 벌크 안전 검증. 기준이 바뀔 때마다 배포하지 않으려면 운영자가 Setup에서 바꿀 수 있어야 한다.

## D5 · 2026.10.11 — 트리거

출처: daily-log D5 「결정 사항」 #1 · #2 · #3 · #5 · #6

- **트리거 규칙은 상태 전이 검증 · 판정 세팅 · 최근 정기점검일 3개, 시정조치 기한은 Flow 유지** — 기한은 같은 레코드 필드만 채우는 단순 계산이고, 나머지는 허용 표 · 예외 · 삭제/복원 재계산이 필요하다.
- **점검 상태 전이는 6개 값으로, '페널티승인대기'는 전이표에서 제외** — 페널티는 시정과 별도로 진행되므로 상태 필드 하나로 동시에 표현할 수 없다. 페널티 진행은 페널티 레코드의 유형 · 승인 상태가 맡는다.
  - (Kai 확인) 요건 정의서 V1.0 §3은 "점검 상태 7개"로 페널티승인대기를 포함하고, org picklist에도 값이 남아 있다. 요건서를 V1.1로 고칠지, picklist 값을 비활성화할지 정해야 한다.
- **판정은 '점검완료'로 바뀔 때 + 점검완료 상태에서 점수가 바뀔 때만 계산, 시정중 이후 고정** — 결과 항목을 하나씩 저장할 때 중간 판정이 찍히는 것을 막는다.
- **날짜 재계산만 `without sharing` 분리 클래스** — SV 재배치 후 이전 SV가 과거 점검을 지우면 편집 권한 없는 가맹점을 갱신해야 한다. 공유를 넘는 범위를 한 클래스로 좁힌다.
- **재귀 방지 static 플래그 대신 `oldMap` 비교** — 실제 재귀 경로가 없고, 플래그는 같은 트랜잭션의 정당한 재실행을 건너뛸 위험이 있다.

## D6 · 2026.10.12 — 테스트 · 비동기 · 설정 데이터

출처: daily-log D6 「결정과 이유」 1 ~ 5

- **판정 테스트는 DB를 타지 않고 `JSON.deserialize`로 Roll-Up 값 주입** — 판정은 Roll-Up 세 값만 보는 순수 계산이다. 경계값마다 insert하면 SOQL · DML이 배로 늘어난다.
- **실패 테스트는 "막혔다"가 아니라 "이 이유로 막혔다"까지 검증** — 저장 실패만 보면 다른 이유로 막혀도 통과한다. `Database.update(ins, false)`로 오류 메시지와 필드까지 Assert한다.
- **BR-05 지연 처리는 Batch + Schedulable** — "한 트랜잭션 한도를 넘는가"로 골랐다. 가맹점이 늘면 쿼리 행 50,000을 넘으므로 청크마다 한도가 리셋되는 Batch여야 한다.
- **Batch는 호출만, 로직은 Service** — D5의 "트리거는 호출만" 원칙을 실행 방식만 바꿔 적용. 같은 로직을 배치 · 화면 · 테스트에서 같은 입구로 부른다.
- **기준값은 Custom Setting이 아니라 Custom Metadata** — 합격선 · 시정선은 값까지 운영 org로 따라가야 하는 업무 정책이다. Custom Setting은 데이터를 org마다 다시 넣어야 한다.

## D7 · 2026.10.13 — LWC 기초 · 데이터 연동

1. **상세(SC-02)는 `lightning-record-form`(LDS)로, Apex 없이** — 레코드 1건 CRUD는 캐시 · 동기화 · FLS를 플랫폼이 준다. 판정 패널만 `@wire(getRecord)`: `recordId` 하나로 조회가 정해지기 때문.
2. **목록(SC-04)은 칩 · 검색 · 정렬 · 페이징 전부 imperative 한 경로로** — 처음엔 칩만 `@wire`로 생각했으나, 같은 Apex를 두 방식으로 부르면 늦게 온 응답이 화면을 덮어쓰고 조건 객체도 둘로 갈라져 통일했다. 정렬 · 페이징은 서버(`ORDER BY` · `LIMIT/OFFSET`), OFFSET 최대 2,000은 알고 선택.
3. **칩은 LWC가 "칩 → 상태 목록"을 갖고, Apex는 `Status__c IN :statuses`만** — 업무 묶음이 바뀌어도 Apex는 그대로. 칩은 해야 할 점검(점검예정) · 시정 대기(시정중 + 지연) · 전체 3개. 「점검중」은 요건서 §3과 D5 전이표 어디에도 없는 값이라 제외(설계 초안 오류).
4. **판정(`Judgement__c`)은 레이아웃 Read-Only + FLS 읽기 전용, 두 겹을 유지** — 관리자 화면에서 판정에 연필이 보여 org를 확인했더니, 권한 매트릭스 V1.2대로 레이아웃 `Readonly` · SV · 권역팀장 · 조회전용 FLS 편집 불가가 **이미 걸려 있었다**. 연필은 System Administrator의 "Edit Read Only Fields" 권한 때문이라 org 설정은 바꾸지 않았다. 둘 다 필요한 이유: D5에서 판정을 점검완료 · 점수 변경 때만 계산하게 했으므로 손으로 고친 값을 아무도 되돌리지 않고, 레이아웃 Read-Only는 관리자 권한으로 넘을 수 있어 FLS가 진짜 잠금이다. 트리거는 시스템 모드라 계속 쓴다. 확인은 관리자가 아닌 김 길동 계정으로.
5. **에러는 `reduceErrors({ body: event.detail })` + `ShowToastEvent`(sticky)** — record-form 에러에는 `body`가 없어 그대로 넘기면 D5 메시지 대신 일반 문구가 나온다.

### 구현하면서 추가로 정한 것

- **목록 조회는 `Database.queryWithBinds(..., AccessLevel.USER_MODE)`** — 바인드 값을 맵으로 넘겨 사용자 입력이 SOQL 문자열에 섞이지 않게 하고, sharing에 더해 FLS까지 현재 사용자 기준으로 강제한다. 정렬 컬럼 · 방향은 바인드할 수 없어 화이트리스트로 검증한다.
- **정렬 끝에 `NULLS LAST, Name ASC`를 붙여 순서를 고정** — 점검일이 같은 행이 여럿이면 DB가 순서를 보장하지 않아 OFFSET 페이징에서 중복 · 누락이 생긴다.
- **목록은 한 컴포넌트로 먼저, 칩 · 검색창 · 페이저 분리는 D8** — 나누는 건 코드를 옮기는 일이라 언제든 할 수 있지만, 처음부터 나누면 깨졌을 때 어느 경계의 문제인지 가리기 어렵다.
- **시연 데이터는 되돌리지 않고 매번 새로 만든다(`scripts/apex/`)** — 점검완료 → 점검예정은 D5 트리거가 막는다. 시연용 레코드에는 `DEMO-` 표시를 달아 리허설로 생긴 시정조치까지 찾을 수 있게 한다.
