## 1. 역할 정의

가상 고객사 **㈜한끼정성**(한식 프랜차이즈 본사)의 가맹점 점검 업무 기준이다.

| 역할              | 테스트 사용자 | 업무                                 | 데이터 범위           |
| ----------------- | ------------- | ------------------------------------ | --------------------- |
| SV (슈퍼바이저)   | 김 길동       | 담당 권역 가맹점 방문·점검·시정 요청 | **본인 담당 매장만**  |
| 권역팀장          | 박 팀장       | 권역 SV 관리, 페널티 승인            | **자기 권역 SV 전원** |
| 조회전용 (경영진) | 최 대표       | 전사 현황 열람                       | **전사, 읽기만**      |
| 영업관리팀장      | 이은석 kai    | 가맹점 등록, 전사 관리               | 전사                  |

**설계 전제**: SV끼리는 서로의 매장·점검을 볼 수 없다. (고객 요구사항)

## 2. 라이선스 · 프로필

| 사용자     | 라이선스            | 프로필                      | Role              |
| ---------- | ------------------- | --------------------------- | ----------------- |
| 김 길동    | Salesforce Platform | 가맹점점검 SV               | SV - 수도권       |
| 박 팀장    | Salesforce Platform | 가맹점점검 권역팀장         | 권역팀장 - 수도권 |
| 최 대표    | Salesforce Platform | 가맹점점검 조회전용(경영진) | **없음** (의도적) |
| 이은석 kai | Salesforce          | System Administrator        | 영업관리팀장      |

**Salesforce Platform 라이선스를 쓴 이유**

- Dev org의 Salesforce 라이선스가 2개뿐이라 테스트 사용자 3명을 만들 수 없었다.
- 본 업무는 Account + 커스텀 오브젝트만 쓰고 Opportunity·Case·Campaign을 쓰지 않으므로
  Platform 라이선스로 기능 제약이 없다. **필요한 권한만 주는 라이선스 선택**이기도 하다.
- 표준 `Read Only` 프로필은 Salesforce 라이선스 전용이라 쓸 수 없어,
  `Standard Platform User`를 복제해 쓰기 권한을 제거하는 방식으로 조회전용을 구성했다.

## 3. 오브젝트 권한 — "무엇을 볼 수 있는가"

Profile로 설정한다. `C`=생성 `R`=읽기 `E`=수정 `D`=삭제

| 오브젝트                                     | SV    | 권역팀장 | 조회전용 | 영업관리팀장 | 비고                                               |
| -------------------------------------------- | ----- | -------- | -------- | ------------ | -------------------------------------------------- |
| 가맹점 (Account)                             | R E   | R E      | R        | C R E D      | 가맹점 등록·삭제는 본사만                          |
| 담당자 (Contact)                             | R E   | R E      | R        | C R E D      |                                                    |
| 점검 (Inspection__c)                         | C R E | C R E    | R        | C R E D      | 소유자 = 배정 SV 또는 Queue                        |
| 점검 결과 항목 (InspectionResult__c)         | C R E | C R E    | R        | C R E D      | 점검의 M-D 자식 — 권한은 부모 점검을 따름          |
| 점검 항목 템플릿 (InspectionTemplateItem__c) | R     | R        | R        | C R E D      | 수정은 권한 집합 `점검표 관리`로                   |
| 시정조치 (CorrectiveAction__c)               | C R E | C R E    | R        | C R E D      | 결과 항목의 M-D 자식                               |
| 페널티 (Penalty__c)                          | R     | C R E    | R        | C R E D      | 소유자여도 SV는 읽기만 (오브젝트 권한이 먼저 막음) |

### 권한 집합 (Permission Set)

| 권한 집합   | API Name                       | 부여 대상      | 주는 권한                                                       |
| ----------- | ------------------------------ | -------------- | --------------------------------------------------------------- |
| 점검표 관리 | `InspectionTemplateManagement` | 본사 운영 담당 | 점검 항목 템플릿 `C R E D` + View All · **Modify All**, 탭 표시 |

**왜 프로필이 아니라 권한 집합인가**: 점검표를 관리하는 사람은 직군이 아니라 *담당*이다.
SV 중 한 명이 겸할 수도 있고 본사 직원일 수도 있다. 프로필을 새로 만들면
"점검표를 관리하는 SV" 프로필이 또 필요해진다. 권한 집합은 기존 프로필 위에 얹기만 하면 된다.

**왜 Modify All까지 주는가**: 템플릿 OWD가 Public Read Only라서 Edit 권한만으로는 _본인이 만든_ 템플릿만 수정할 수 있다.
관리자가 등록한 양식을 운영 담당이 고치려면 소유자와 무관하게 수정하는 Modify All이 필요하다.

**필드 권한(FLS)**: 총점·배점 합계·필수 미흡 수(Roll-Up)와 판정·점검번호(이관)·가맹점 매장코드·권역·사업자번호·오픈일은 관리자 외 **읽기 전용**.
필수 Lookup(가맹점)과 M-D 필드는 FLS 설정 대상이 아니다(항상 표시).

## 4. 레코드 권한 — "어느 레코드까지 볼 수 있는가"

### 4.1 OWD (조직 전체 기본값)

| 오브젝트                  | Internal                   | External             | Grant Access Using Hierarchies |
| ------------------------- | -------------------------- | -------------------- | ------------------------------ |
| Account and Contract      | **Private**                | Private              | 강제 (표준 오브젝트)           |
| Contact                   | Controlled by Parent       | Controlled by Parent | 강제                           |
| 점검 (Inspection__c)      | **Private**                | Private              | ✅                             |
| 점검 결과 항목 · 시정조치 | Controlled by Parent (M-D) | Controlled by Parent | 부모를 따름                    |
| 점검 항목 템플릿          | **Public Read Only**       | Private              | ✅                             |
| 페널티 (Penalty__c)       | **Private**                | Private              | ✅                             |

> 커스텀 오브젝트는 `Grant Access Using Hierarchies` 체크를 끌 수 있다.
> 끄면 Role 계층이 동작하지 않아 권역팀장이 SV의 점검을 보지 못한다. 반드시 켜 둔다.

### 4.2 Role 계층

```
영업관리팀장 (SalesAdminManager)          ← 이은석 kai
  ├─ 권역팀장 - 수도권 (RegionManagerCapital)   ← 박 팀장
  │     └─ SV - 수도권 (SupervisorCapital)       ← 김 길동
  └─ 권역팀장 - 영남 (RegionManagerYeongnam)
        └─ SV - 영남 (SupervisorYeongnam)
```

- 영남 권역은 조직 구조를 보이기 위해 만들어 두고 사용자는 배정하지 않았다.
- 계층은 **위에서 아래로만** 동작한다. SV는 팀장이 소유한 레코드를 볼 수 없다.

### 4.4 Queue

| Label       | API Name               | 대상 오브젝트 | 멤버                                       | 용도                                                |

## 5. 설계 근거

### 5.1 조회전용 경영진을 Role 계층에 넣지 않은 이유

Role 계층은 상위 역할에게 하위 레코드의 **읽기와 쓰기를 함께** 상속한다(Grant Access Using Hierarchies).
최 대표는 열람만 필요하므로 계층에 넣으면 불필요한 쓰기 권한까지 갖는다.
공유 규칙은 접근 수준을 `Read Only`로 **지정**할 수 있으므로 열람 전용에는 공유 규칙이 맞다.

| 도구      | 쓰는 상황                                    | 주는 권한        |
| --------- | -------------------------------------------- | ---------------- |
| Role 계층 | 업무상 개입하는 상사 (팀장이 SV 점검을 수정) | 읽기 + 쓰기      |
| 공유 규칙 | 조직도 밖 열람자 (경영진·감사)               | 읽기만 지정 가능 |

### 5.2 공유 대상을 사용자가 아니라 Public Group으로 한 이유

공유 규칙은 사용자 개인에게 직접 부여할 수 없고 Role 또는 Group에만 줄 수 있다.
Group을 쓰면 감사·CFO가 추가될 때 **규칙을 수정하지 않고 그룹에 멤버만 추가**하면 된다.
운영 이관 시 담당자가 건드릴 범위가 작아진다.

### 5.3 공유 범위를 `Roles`가 아니라 `Roles and Internal Subordinates`로 한 이유

`Roles: 영업관리팀장`은 그 Role에 속한 사용자(Kai)가 소유한 레코드만 공유한다.
SV·권역팀장이 소유한 가맹점이 빠지므로 `Roles and Internal Subordinates`를 선택했다.

## 6. 검증 결과 (Login As)

검증일 2026.10.04 · 대상 데이터: 가맹점 4건 + 기존 샘플 14건 = 18건

| #   | 시나리오                                        | 기대 결과                            | 실제 결과                                | 판정 |
| --- | ----------------------------------------------- | ------------------------------------ | ---------------------------------------- | ---- |
| 1   | 김 길동으로 `모든 계정` 조회                    | 본인 소유 2건                        | 강남점·역삼점 2건                        | O    |
| 2   | 김 길동이 박 팀장 소유 수원점 **URL 직접 입력** | 접근 거부                            | "액세스하려는 레코드를 찾을 수 없습니다" | O    |
| 3   | 박 팀장으로 `모든 계정` 조회                    | 본인 1건 + SV 2건 = 3건, 판교점 제외 | 강남·수원·역삼 3건                       | O    |
| 4   | 최 대표로 `모든 계정` 조회                      | 공유 규칙 범위 전체                  | **17건**                                 | O    |
| 5   | 최 대표 화면의 `새로 만들기` 버튼               | 없음                                 | 없음                                     | O    |

**시나리오 4의 17건 / 18건**
빠진 1건은 `Sample Account for Entitlements`이고 소유자가 `Process Automated`(Role 없는 시스템 계정)다.
공유 규칙을 `Roles and Internal Subordinates`로 걸었으므로 **Role 계층 밖 소유자의 레코드는 공유되지 않는다.**
설계가 의도대로 동작함을 건수로 확인한 사례다.

**시나리오 2의 의미**
목록에 보이지 않는 것만으로는 "숨긴 것"인지 "권한이 없는 것"인지 구분되지 않는다.
URL 직접 접근이 차단되는 것이 레코드 수준 보안이 실제로 작동한다는 증거다.

### 6.2 커스텀 오브젝트 접근 검증

검증일 2026.10.06 · 시연 데이터: 점검 4건(소유자 김 길동·박 팀장·Kai·Queue), 결과 항목 4건, 시정조치 1건, 페널티 1건
org가 계산한 접근 권한(`UserRecordAccess`) 결과이며, **세 사용자로 Login As 하여 점검·페널티 목록과 편집 버튼 유무가 표와 일치함을 확인했다** (2026.10.06).

| 레코드                         | 김 길동 (SV) | 박 팀장 (권역팀장) | 최 대표 (조회전용) | 근거                                          |
| ------------------------------ | ------------ | ------------------ | ------------------ | --------------------------------------------- |
| 점검 · 강남점 (김 길동 소유)   | RW           | RW                 | R                  | 본인 / 계층 / 공유 규칙                       |
| 점검 · 수원점 (박 팀장 소유)   | **—**        | RW                 | R                  | SV는 상위 소유 레코드를 못 봄                 |
| 점검 · 판교점 (Kai 소유)       | —            | **—**              | R                  | 팀장도 상위 소유 레코드를 못 봄               |
| 점검 · 역삼점 (미배정 Queue)   | RW           | RW                 | **—**              | Queue 멤버만 접근                             |
| 결과 항목 (강남점 점검의 자식) | RW           | RW                 | R                  | M-D — 부모 점검과 동일                        |
| 템플릿                         | R            | R                  | R                  | Public Read Only                              |
| 페널티 · 강남점 (김 길동 소유) | **R**        | RW                 | R                  | SV 프로필이 페널티 `R` — 소유자여도 수정 불가 |
